# CI 全托管完整性审计（#423，2026-09-02）

## 结论
当前调度为**四重冗余**架构，单点失败已被充分对冲，整体健壮性高。无致命缺口；列出 2 处可改进项（非阻塞）。

## 调度拓扑
| 层级 | 文件 | 触发 | 职责 | 关键防护 |
|---|---|---|---|---|
| 主调度 | `stock.yml` | 13+ cron + dispatch | 盘前/竞价/盘中/收盘/复盘/周末+妖股 | concurrency 锁防并发改库；Release 资产跨次续存状态 |
| 执行器 | `executor.yml` | 11 cron（含 09:28 备份开仓） | 模拟盘开仓/巡逻/尾盘/复盘 | cron 表达式映射任务（延迟不误判）；EXEC_ACCOUNT_JSON 注入；状态走 Release |
| 看门狗 | `watchdog.yml` | 14 密集检查点 | 主调度漏投时 15~40min 内救场 | 以 `push_log.jsonl` 当日 mode 去重，不盲发/不重复轰炸 |
| 外部备份 | `scheduler-backup.yml` | 外部 15min 定时器 | 给 stock.yml 加第二条独立触发链 | 与 GitHub cron 解耦 |
| 补派链 | `stock.yml:dispatch-executor` | 每次 stock 运行顺手派 executor | 给模拟盘加第二触发源 | 时段闸 + 执行器任务账本幂等拦截 |

## 单点失败（SPOF）对冲验证
- **GitHub cron 漏投**：executor 09:25 主 + 09:28 备份 cron；stock 侧另有 watchdog + scheduler-backup + dispatch-executor 三重补派。✅
- **cron 延迟导致任务错配**：executor 改用 `github.event.schedule` 的 cron 表达式映射任务（非运行时刻），延迟 24min 也不误判。✅
- **状态丢失（去重账本/数据）**：`data-snapshot` Release 资产（market.db.gz + state.tar.gz）每次运行前恢复、后回存，gh release upload 带 `retry()` 3 次重试。✅
- **权限不足**：executor.yml / stock.yml / watchdog.yml 均显式 `actions: write`（dispatch 他 workflow 必需）；watchdog 显式 `GH_REPO` 修复非仓库目录 gh 调用。✅
- **凭据缺失**：executor 缺 `EXEC_ACCOUNT_JSON` 会「未配置 account 退出」——已在 env 注释固化，属配置项非代码缺陷。✅

## 发现的可改进项（非阻塞，建议后续）
1. **执行器「零操作」无主动告警**：若 executor 全部触发链在某日同时失效（极低概率），sim.db 会静默停滞，仅网站「心跳」字段 `stale` 被动提示，无主动推送告警。建议加一条「连续 N 日无 executor 成功运行 → PushPlus 告警」。
2. **看门狗依赖 state.tar.gz 落地**：若 stock.yml 回存步骤失败（网络），watchdog 拿不到 `push_log.jsonl` 会保守跳过（安全但不救场）。与 #1 同源风险，已在回存步骤 `retry(3)` 缓解。

## 本次不涉及代码改动
审计结论为「架构层面已健全」，#423 交付物即本报告 + 上述 2 条建议。
